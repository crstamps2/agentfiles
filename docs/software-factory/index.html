How it runs

One ticket, one workspace, one line

Every admitted ticket follows the same sequence: spinup → plan → plan-review → implement → gates → draft-pr → ready → bot-loop → human-gate-1. Failures go to recorded recovery. Real product questions go to a person.

Workstations

The factory floor is an Orca board

Each admitted ticket gets its own Orca workspace: a worktree cut from origin/main, a setup terminal, a dev server, a Pi agent in an Orca chat session, and reference and app browser tabs. The workspace's status lane is how people and the loop hand work back and forth.

Restart-safe workstations

Every workspace action leaves a receipt

Creating the worktree, running setup, starting the dev server, and launching the agent each record a receipt in the ticket's workspace binding. After a crash or restart, the loop checks what already exists. An uncertain step is inspected and never blindly replayed, so a restart cannot spawn a second agent.

Liveness checks

Liveness comes from Orca, not the UI

The loop confirms an agent by its durable Orca chat session ID and confirms the dev server by its running terminal plus a live HTTP probe. If Orca's window drops a pane while the process keeps running, the ticket keeps going. A finished setup terminal does not count as a missing resource.

Context

Where it sits

“Software factory” covers two operating models in current AI practice. This line is the first kind, by design.

This model

Governed AI software factory

A repeatable delivery system that connects specifications, agents, orchestration, verification, permissions, and human decision gates. AWS's AI-driven development lifecycle keeps human clarification and approval. GitHub's spec-driven and Continuous AI workflows produce reviewable artifacts. Microsoft's agentic platform builds governance into each stage.

Sources: AWS AI-DLC, GitHub Spec Kit, Continuous AI, Microsoft.

A stricter model

Dark software factory

Specifications and scenarios drive implementation with no routine human coding or code review. External behavioral validation carries the trust that review usually carries.

“Code must not be written by humans.”
“Code must not be reviewed by humans.”

StrongDM's stated constraints, not a universal maturity bar. Source. This line keeps human review on purpose.

Roadmap

What's next on the line: proving yield

The next milestone is evidence that the existing line produces acceptable changes with little intervention and known cost. Raising capacity or removing safeguards is a separate decision.

Measure

Run a consecutive batch and count

  • Share of tickets reaching Human Gate 1 without rescue
  • Human minutes per accepted ticket
  • Median and slow-tail lead time
  • Total cost, including failed attempts and repair
  • Rework after review and escaped regressions

On Hold hand-backs are recorded in cohort history as operator-on-hold, which makes interventions countable.

Accept independently

Add a protected scenario suite

  • Existing click and submit behavior
  • Keyboard, focus, and accessibility
  • Narrow screens and overflowing content
  • Client-side navigation and caching
  • Visual checks of compiled assets

Correctness should be shown outside the builder's own account of success.

Harden

Retire recurring failure classes

Recovery and test-first runner repair are in place. The useful measure is whether each rescue class stops recurring, shown by the original failing gate passing with an exact verification receipt.

Prove unattended

Ordinary failures resolve while the operator is away

The goal is routine failures fixing themselves and real product questions reaching the operator with useful evidence. A small, bounded cohort is the right proving ground.

Human release authority stays

Approval, communications, merge, and deployment rules are deliberate boundaries. A dependable factory can keep people in charge of release.

Adopting it

Run your own line

You can borrow the practices, pilot one ticket, or stand up a full line. Each step works on its own.

Lightweight

Borrow the practices

Start with the shared instructions, role definitions, skills, and verification habits in your current tool. Setup paths exist for Pi, Claude Code, and Codex CLI; the autonomous runner is Pi-based. No intake, Orca board, or supervisor needed.

Supervised pilot

Try one bounded ticket

Pick one explicitly owned ticket with clear acceptance criteria and a spend expectation. Run it interactively in its own worktree and watch each stage before letting anything run in the background.

Setup sequence

  1. Read the guide and policy. Start with the README, the agent-loop operator guide, and the operations policy, which is the authority on ownership and recovery.
  2. Install tooling. Python 3.11+, Pi 1.3.0+ with pi-subagents, Node.js, Git, GitHub CLI, issue-tracker access, and model-provider access. The repository supplies no credentials; keep them in environment variables or your credential store.
  3. Install Orca. Put its CLI on your PATH (orca, or orca-ide on Linux) and register your app checkout. Before creating anything, the runner confirms Orca is reachable, the repo matches, and the Orca build reports the capabilities the adapter needs.
  4. Create your private config. Copy hopper.example.toml to hopper.toml, fill in project, workspace, Orca status IDs, paths, budgets, and cohort capacity, then set project.configured = true. The runner refuses to act on a missing or incomplete file and never falls back to the template. Never commit hopper.toml.
  5. Inspect, then pilot. Run the read-only commands below. A real drip creates Orca workspaces and starts agents, so run it only when you mean to, and start with one supervised ticket.
Read-only inspection in a fresh checkout
git clone https://github.com/crstamps2/agentfiles.git
cd agentfiles
./bootstrap.sh --tool=pi --repo="$PWD" --dry-run

cd common/skills/agent-loop
cp -n hopper.example.toml hopper.toml   # then edit it
R="$PWD/scripts"
python3 "$R/runner.py" overview
python3 "$R/runner.py" drip --dry-run

Dropping --dry-run from bootstrap has your CLI run its setup document and can change your harness configuration.

Portable framework, project-specific line

The framework supports macOS and Linux. A full line also relies on launchd supervisors and on target-app conventions in the Orca adapter's dev-server probe: bin/dev under overmind, a PORT in .env, and a per-ticket local .test hostname. Another app needs those pieces adapted.

Bottom line

A specialized software factory: tickets enter, Orca workspaces build them, and people review what comes out.

The assembly line exists. What remains is showing it delivers acceptable changes consistently, with little intervention and a known cost.
